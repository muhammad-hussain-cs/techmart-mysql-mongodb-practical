3. MySQL - Relational Tables + Reports

customers (customer_id PK)  →  orders (customer_id FK, product_id FK)  ←  products (product_id PK)

SELECT c.city, COUNT(o.order_id) AS orders, SUM(o.quantity * p.price) AS sales
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN products  p ON o.product_id  = p.product_id
WHERE o.status <> 'Cancelled'
GROUP BY c.city ORDER BY sales DESC;

4. MongoDB - Same Data as Documents

No tables and no JOIN - each customer is one document and his orders sit inside it as an array:

{
  "_id": 1,
  "full_name": "Ahmed Khan",
  "city": "Lahore",
  "email": "ahmed.khan@gmail.com",
  "phone": "0301-2345671",
  "orders": [
    { "product": "Wireless Mouse", "price": 1800, "quantity": 2,
      "amount": 3600, "status": "Delivered" },
    { "product": "Laptop Stand", "price": 2500, "quantity": 1,
      "amount": 2500, "status": "Delivered" }
  ]
}
// Sales by city - aggregation pipeline (MongoDB's GROUP BY)
db.customers.aggregate([
  { $unwind: "$orders" },
  { $match: { "orders.status": { $ne: "Cancelled" } } },
  { $group: { _id: "$city", sales: { $sum: "$orders.amount" } } },
  { $sort: { sales: -1 } }
])

Result is identical to MySQL: Total Sales = Rs 195,700

5. MySQL vs MongoDB - When I Use Each

MySQLMongoDB
Data stored asTables with rows & columnsJSON-like documents
SchemaFixed - defined firstFlexible - can vary per document
Linking dataJOIN + Foreign KeysEmbedded arrays / references
Best forOrders, payments, structured recordsCatalogues, flexible / fast-changing data
